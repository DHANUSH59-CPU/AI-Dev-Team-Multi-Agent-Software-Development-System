What Is This Thing? §1

Think of it as a software company staffed entirely by AI. A customer walks in and says "build me a todo app." A Project Manager asks clarifying questions. An Architect draws up the blueprint. A Planner writes the task board. Coders write one file at a time. A Reviewer checks each file. A Tester runs it in a sealed room. A Debugger fixes failures. And a Photographer takes a snapshot after every step so nothing is ever lost.

The "sealed room" is Docker. The "photographer" is Redis. The whole company is wired together by LangGraph. The brain every employee calls when they need to think is Google Gemini 2.5 Flash.

The one-sentence answer (say this first in interviews) "I built a Python system with 27 specialized AI agents that turns a plain-English requirement into a fully deployed application — backend, database, frontend — using LangGraph, Gemini, Docker, and Redis, for about 13 cents per app."

Why does this matter to an interviewer?

It touches almost everything they care about: LLM integration, system design, state management, Docker/containers, async Python, databases, REST APIs, WebSockets, error handling, and cost optimization — all in one project. When you describe it well, they have no choice but to keep asking follow-up questions. That is the position you want to be in.

The 7 Phases — Walk Through These Calmly §3

Memory sentence — say it 3 times "Please All Programmers: Don't Quit During Production"
PM → Architect → Planner → Dev Loop → Quality → Deploy → Present
Phase 1 — PM Agent 2 LLM calls
Takes the user's vague requirement and turns it into a structured specification. If it's ambiguous, asks 3 to 8 clarifying questions — one call for questions, one call for the final spec. Output: clarifiedSpec (app name, features, pages, DB recommendation, user roles). Questions come through the terminal or dashboard WebSocket.
Phase 2 — Architect 5 LLM calls + 1 validator (free)
Five sequential steps, one LLM call each: entities & naming conventions, DB schema, API endpoints, frontend pages, folder structure. Then the Blueprint Validator — pure Python, zero tokens — does 5 cross-checks (routes reference real tables, valid foreign keys, no orphan tables, consistent auth, consistent naming). Use this to show off: "I chose deterministic code validation over LLM validation because you need guarantees, not probabilities."
Phase 3 — Planner + Sandbox 1 LLM call
Planner breaks the blueprint into 15–25 ordered tasks across 7 sub-phases (setup, models, middleware, backend routes, frontend pages, integration, deployment). Then spins up 3 Docker containers — PostgreSQL (or MongoDB), Node backend, React frontend — all on the same Docker network. Health-checks that all three can communicate before proceeding.
Phase 4 — Dev Loop ⭐ THE CORE ~50 LLM calls
13 nodes that cycle through every task. Code → Review → Execute in Docker → Snapshot. When something fails, the Debugger escalates through 3 tiers. When the reviewer rejects 3 times, the task gets simplified. Every success saves a rollback snapshot. This is where ~80% of the interesting engineering is. See Section 4 for the full diagram.
Phase 5 — Quality 1 call per phase
After each dev phase completes, a Pattern Extractor reads the finished code and identifies conventions — error handling format, naming style, import patterns — and injects these into the shared state. The next phase's coder reads these patterns, keeping the whole codebase consistent. Without this, each phase's code looks like it was written by a different person.
Phase 6 — Deploy 0 LLM calls
Runs docker-compose up and verifies: PostgreSQL is running ✓, backend HTTP responds ✓, frontend is accessible ✓, API can reach the database ✓. Pure Python — no LLM tokens spent. If verification fails, the Debugger agent is called.
Phase 7 — Present 0 LLM calls
Returns the final app path, docker-compose command, generated README, all files, and a cost summary. Done. The user has a working app.

The Context Builder — say "this is like RAG"

this impresses
interviewers.
use the term.

Before the coder writes a file, contextBuilder fetches everything that file will need: what imports are available, what functions other files export, what coding patterns were established earlier. This is retrieval-augmented generation applied to code context. The lookup itself is pure Python, zero LLM tokens:

  1. Exact match — Python dict lookup, O(1)
  2. Fuzzy match — partial string scan, O(n)
  3. Disk fallback — regex scan of file contents

Why one file per LLM call?

Large outputs get truncated mid-JSON. The Gemini API cuts off at the token limit, leaving you with broken output. By generating one file at a time, outputs stay small and complete. Yes, it means more API calls — but every call succeeds cleanly. The trade-off is deliberate.

The snapshot — it's a stack

After every successful file: copy.deepcopy(state) is pushed onto a list. On rollback: snapshots.pop(). Classic stack. The deep copy matters — a shallow copy would mean later changes corrupt the snapshot.

Project-Specific

Why LangGraph instead of plain Python functions?
With 27 nodes, plain functions become spaghetti — you lose track of who calls what and state gets passed around inconsistently. LangGraph forces every node to communicate only through a shared state object with defined reducers. It also handles conditional routing, loops, and checkpointing natively. The structure scales cleanly as you add nodes.
What are reducers? Give examples.
Rules for merging incoming state with existing state. Three types: last-write — new value replaces old (used for currentTask); merge_objects — shallow dict merge {**old, **new} (used for blueprint); accumulate — append to list (used for conversation history and file registry). Each node is a pure function: state in, state out.
Why checkpoint to Redis after every single node?
A full run takes 30–60 minutes and makes 100+ API calls. Without checkpointing, any crash means restarting from zero and paying for all those API calls again. With Redis, LangGraph resumes exactly from the last completed node. I also built a fallback to in-memory checkpointing if Redis is unavailable — so the system degrades gracefully.
Why is the Blueprint Validator written in Python instead of asking the LLM?
Validation needs guarantees, not probabilities. The validator checks five structural invariants — every API route references a real table, all foreign keys are valid, no orphan tables, consistent auth, consistent naming. A Python function checking these is 100% accurate, instant, and costs zero tokens. An LLM might hallucinate "looks fine" when it's not.
How does human-in-the-loop work without blocking the event loop?
The InputBridge pattern: the agent emits a WebSocket event to the dashboard and then awaits an asyncio.Future(). When the user submits their answer, the WebSocket handler calls future.set_result(answer) which resolves the Future and the agent resumes. The event loop is never blocked — other coroutines keep running while waiting for human input.
What happens when generated code fails? Walk me through it.
Executor runs the code in Docker and it fails. Control goes to debuggerAgent, which tries three escalation tiers: Tier 1, fix using just the local error context; Tier 2, fix with broader codebase context; Tier 2.5, roll back to the last successful snapshot and retry; Tier 3, emit a human-escalation request and wait. Meanwhile if the reviewer has rejected the same task three or more times, simplifyTask breaks it into smaller sub-tasks. Both paths feed back into the coder — the loop terminates either by passing the executor or by a human saying skip.

Python Concepts

Where did you use asyncio, and why not threads?
The workload is I/O-bound — waiting on Gemini API, Redis, Docker commands — not CPU-bound. asyncio handles hundreds of concurrent I/O waits on a single thread by switching at await points. Threads would hit Python's GIL for CPU tasks and add synchronization overhead for no benefit here. FastAPI, the Gemini calls, the Redis checkpointing, and the InputBridge all use async/await.
Why deepcopy for snapshots rather than shallow copy?
Shallow copy shares references to nested objects. If I shallow-copy the state and then the active run modifies a nested dict, the snapshot is silently corrupted. copy.deepcopy() produces a completely independent copy — modifying the live state later cannot affect it. The merge_objects reducer uses shallow merge because it's creating a fresh dict from two separate sources, which is fine. The snapshot must be a true independent clone.
What OOP principles did you apply?
Encapsulation — each agent class owns its prompt and parsing logic privately. Inheritance — a BaseAgent holds the common Gemini call, retry logic, and token tracking; specific agents extend it. Polymorphism — all agents implement run(state), so LangGraph calls them uniformly without caring which agent it is. Abstraction — SandboxManager hides all Docker complexity behind create(), execute(cmd), and cleanup().

DSA

Name the data structures used and where.
Queue (task queue — FIFO), Stack (snapshot history — push on success, pop on rollback), HashMap/dict (file registry — O(1) filename lookup), DAG (LangGraph itself — 27 nodes plus directed conditional edges), append-only list (event log, conversation history, token records).
Write code to detect a cycle in the task dependency graph.
def has_cycle(graph: dict[str, list[str]]) -> bool:
    WHITE, GRAY, BLACK = 0, 1, 2
    color = {node: WHITE for node in graph}

    def dfs(node) -> bool:
        color[node] = GRAY
        for neighbor in graph.get(node, []):
            if color[neighbor] == GRAY:    # back edge = cycle
                return True
            if color[neighbor] == WHITE and dfs(neighbor):
                return True
        color[node] = BLACK
        return False

    return any(dfs(n) for n in graph if color[n] == WHITE)
DFS with 3-color marking. GRAY means "currently on the recursion stack." Finding a GRAY neighbor means we found an edge back to an ancestor — that's a cycle. Time: O(V + E).

What was the hardest bug?
LLM JSON truncation. Gemini would cut off mid-JSON when the output hit the token limit. I built a five-tier repair pipeline: detect a MAX_TOKENS finish reason, try to close unclosed JSON brackets, extract partial JSON, retry with a smaller prompt, or fall back to requesting just the critical parts. Then I prevented it permanently by switching to one-file-per-call — outputs stay small enough to never truncate.
What would you improve if you had more time?
Three things: replace the file-registry-based context with a vector database for semantic retrieval — proper RAG instead of string matching. Add parallel task execution within a phase, since tasks in the same phase are often independent. And add a provider abstraction so the system can fall back to Claude or GPT-4 if Gemini is rate-limited.
How does this scale to larger applications?
State-driven architecture helps — no direct node-to-node calls means adding nodes doesn't break existing ones. The token budget would need raising for larger apps. Parallel execution within phases would cut wall-clock time significantly. The Docker sandboxes are already isolated per project, so horizontal scaling is mostly a matter of running multiple graph instances.
