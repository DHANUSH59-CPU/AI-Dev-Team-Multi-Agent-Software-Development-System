1. Project Overview

The One-Liner: An autonomous multi-agent AI system that takes a plain English requirement like "build a todo app" and automatically generates the entire software project — from specifications to working code — using 27 specialized AI agents working together like a real software team.

What problem does it solve?

Software development has many manual steps: gathering requirements, designing architecture, planning tasks, writing code, reviewing, testing, and debugging. This project automates the entire pipeline using AI agents, where each agent is a specialist (like a real PM, Architect, Coder, Reviewer).

What can it do?

  • Accept a vague requirement and ask clarifying questions
  • Design complete system architecture (DB schema, API endpoints, frontend pages)
  • Plan tasks into ordered phases
  • Write actual code for the entire application
  • Review code quality and execute it for testing
  • Self-debug when tests fail
  • Escalate to humans when stuck
  • Track LLM token usage and costs in real-time
  • Show all of this on a live React dashboard
Real-world analogy: It's like having a virtual software team where you're the client. You say "I need an e-commerce site" and the team (PM, designer, coder, tester) handles everything.

5. The 27 Agents (Organized by Phase)

The system has 7 phases. Each phase has multiple nodes/agents.

Phase 1 Requirements Gathering

PM Agent (pmAgent.js)

Analyzes the user's raw requirement. If unclear, generates 3-8 clarifying questions. Once answered, produces a structured JSON spec with features, pages, DB recommendation.

Human Input Node (humanInput.js)

Pauses the graph and collects answers from the user via terminal or dashboard.

Phase 2 Architecture Design

Architect Agent — 5 Steps (architectAgent.js)

  1. Step 1: Identifies entities (User, Post, Comment...)
  2. Step 2: Designs database schema with tables and fields
  3. Step 3: Defines API endpoints (REST routes)
  4. Step 4: Plans frontend pages and routes
  5. Step 5: Generates the folder structure

Blueprint Validator (blueprintValidator.js)

Checks the entire blueprint for consistency (e.g., does every API endpoint match an entity?). Loops back to fix issues if invalid.

Phase 3 Planning & Sandbox Setup

Planner Agent (plannerAgent.js)

Breaks the blueprint into ordered phases of tasks (Setup → Backend → Frontend → Integration). Each task lists the files to create.

Setup Sandbox (setupSandbox.js)

Creates a Docker container and isolated folder for the project.

Sandbox Health Check (sandboxHealthCheck.js)

Verifies the sandbox is ready and reachable before code starts being written.

Phase 4 The Dev Loop (Most Important!)

Select Next Task (selectNextTask.js)

Picks the next pending task from the queue. Routes to context builder, phase verification, or deployment.

Context Builder (contextBuilder.js)

Gathers all relevant info the coder needs: dependent files, patterns, the task description.

Coder Agent (coderAgent.js)

The actual code writer. Receives context, produces file contents, writes them to the sandbox.

Update Registry (updateRegistry.js)

Tracks every file created with its exports, functions, and metadata.

Reviewer Agent (reviewerAgent.js)

Reviews the generated code for bugs, style issues, missing logic. Outputs: approved, rejected, or needs simplification.

Executor Agent (executorAgent.js)

Actually runs the code inside Docker to check if it works.

Debugger Agent (debuggerAgent.js)

If execution fails, analyzes errors. 3-tier strategy: simple fix, deeper investigation, escalate.

Snapshot Manager (snapshotManager.js)

Saves a checkpoint of working code after every successful task — enables rollback.

Simplify Task (simplifyTask.js)

If a task keeps failing, breaks it into a simpler version.

Human Escalation (humanEscalation.js)

When the system can't proceed, asks the human: skip / provide guidance / simplify.

Phase 5 Quality & Optimization

Phase Verification (phaseVerification.js)

Verifies all tasks in the current phase actually work together.

Pattern Extractor (patternExtractor.js)

Looks at completed code and extracts patterns (naming, error handling) for consistency in future tasks.

State Compactor (stateCompactor.js)

Trims unnecessary data from state to save memory and tokens between phases.

Phase 6 Deployment

Deployment Verifier (deploymentVerifier.js)

Final smoke test — does the complete app actually start and respond?

Present to User (presentToUser.js)

Formats the final output: where files are, how to run, what was built.

Phase 7 Dashboard (Frontend)

Not nodes, but UI components:

  • PipelineVisualizer — shows which agent is running
  • LogStream — live agent output
  • OutputPanel — shows generated files
  • HumanInputPanel — for clarifying questions
  • TokenBudgetBar — tracks LLM costs

7. State Management (LangGraph)

Key Insight: All 27 agents communicate ONLY through a shared state object. No direct function calls between agents. This makes the system loosely coupled and easy to debug.

How State Works

Each field in state has a reducer — a merge function:

  • Simple fields (string, number): last write wins
  • Arrays (file registry, conversation): accumulate (push new items)
  • Objects (blueprint, patterns): merge keys (spread)
  • Token usage: sum totals + append new calls

// From state.js — how fileRegistry accumulates
fileRegistry: Annotation({
  reducer: (existing, incoming) => {
    if (!incoming) return existing;
    if (Array.isArray(incoming)) {
      const map = new Map(existing.map(f => [f.path, f]));
      for (const entry of incoming) {
        map.set(entry.path, entry);  // update or add
      }
      return Array.from(map.values());
    }
    return existing;
  },
  default: () => [],

8. Key Concepts Explained

What is LangGraph?

LangGraph is a framework for building stateful, multi-actor applications with LLMs. Think of it like a state machine where each "state" is a node, and edges define transitions. Instead of writing tangled if-else chains, you describe nodes and edges, and LangGraph handles the flow.

What is a Multi-Agent System?

Instead of one giant AI prompt doing everything, you split work among specialized agents. Each agent has a focused role (PM, Coder, Reviewer). They communicate through shared state. Benefits: Better quality, easier debugging, parallelization possible.

What is Checkpointing?

After every node finishes, the entire state is saved to Redis. If the process crashes, you can resume from the last good state instead of starting over. This is critical because a full run might take 30+ minutes and cost real money in LLM tokens.

What is Sandboxing?

Generated code is untrusted — it could have bugs or be malicious. Running it on your host machine is dangerous. Docker creates an isolated container where the code runs without access to your real filesystem.

What is Token Budgeting?

LLM API calls cost money based on tokens (chunks of text). A runaway loop could rack up huge bills. The system tracks every input/output token, calculates cost, and hard-stops if the budget (e.g., $2.00) is exceeded.

What is Human-in-the-Loop?

Some decisions are too important for AI alone (e.g., "this task keeps failing — should I skip it?"). The system pauses, asks the human, then resumes with their input.

Self-Healing Loop

The dev loop doesn't crash on first failure. It retries, simplifies, debugs, and only escalates when all else fails. This makes the system resilient. 

Code rejected by reviewer?
  -> Retry up to 2 times
  -> If still failing, simplify the task
  -> If simplification fails, escalate to human

Code fails execution?
  -> Debugger tries to fix
  -> If can't fix, escalate to human

Sample: How a Node is Defined

// Every node is just a function: state -> partial state update
async function pmAgentNode(state) {
  const response = await callGemini({
    prompt: `User wants: ${state.userRequirement}. Generate spec or questions.`
  });

  if (response.needsClarification) {
    return {
      pmStatus: "needs_clarification",
      pmQuestions: response.questions,
    };
  }

  return {
    pmStatus: "spec_ready",
    clarifiedSpec: response.spec,
  };
}

11. Interview Questions & Answers

Q1: Explain your project in 30 seconds.
"I built a multi-agent AI system that takes a plain English requirement and automatically generates an entire software project. It uses 27 specialized AI agents — PM, Architect, Planner, Coder, Reviewer, Debugger — orchestrated by LangGraph. Each agent has a specific role, like a real software team. The system also has a React dashboard for real-time monitoring."
Q2: Why did you use multiple agents instead of one big AI prompt?
"A single prompt can't handle the full software lifecycle. Context would explode, hit token limits, and quality would drop. By splitting into specialized agents, each prompt is small, focused, and produces better results. It also lets me debug each step independently."
Q3: What was the hardest technical challenge?
"Coordinating 27 agents without spaghetti code. I solved it using LangGraph's shared-state pattern — nodes don't call each other directly, they read and write to a central state with reducer functions that handle merging. This made the system loosely coupled and easy to extend."
Q4: How do you handle failures?
"Three layers: First, retry — if a coder's output gets rejected by the reviewer, it retries up to 2 times. Second, simplification — if retries fail, the task is broken into a smaller version. Third, human escalation — if even that fails, the system pauses and asks the human. Plus, state is checkpointed to Redis so a crash doesn't lose progress."
Q5: How do agents communicate?
"Through shared state in LangGraph. Each node receives the state, returns updates, and LangGraph applies reducers to merge those updates. For example, the Coder writes to coderOutput, then the Reviewer reads it from state. There are no direct function calls between agents."
Q6: Why Docker for code execution?
"Generated code is untrusted — it could have bugs or be unintentionally harmful. Running it on the host machine is dangerous. Docker isolates each project in its own container, so even if the code breaks, it doesn't affect my system."
Q7: What's the role of Redis?
"Redis is the checkpointer. After every agent finishes, the entire state snapshot is saved to Redis. If the pipeline crashes, I can resume from the last checkpoint using a thread ID. Without this, a 30-minute run could lose all progress."
Q8: How do you keep LLM costs under control?
"Every Gemini call goes through a wrapper that counts input/output tokens and calculates cost. The system has a configurable token budget — when exceeded, it throws an error and stops. There's also a state compactor that trims unnecessary data between phases to keep context size small."
Q9: Why WebSocket for the dashboard?
"The pipeline can run for many minutes. With REST polling, the dashboard would either miss events or hammer the server. WebSocket lets the backend push updates as each agent runs — pipeline state, log lines, token usage — without the client having to ask."
Q10: What would you improve?
"Three things: First, parallelize independent tasks — right now everything is sequential. Second, support multiple LLM providers, not just Gemini. Third, add a CI/CD pipeline so generated projects can deploy automatically to AWS or Vercel."
Q11: What design patterns did you use?
"Several: State Machine (LangGraph), Strategy Pattern (different debugger tiers), Observer Pattern (WebSocket events), Reducer Pattern (state merging), and Circuit Breaker (token budget enforcement)."
Q12: How does the React frontend work?
"It's a Vite + React app with Zustand for state. When the user submits a requirement, it hits the backend via REST. Then a WebSocket connection streams real-time updates — which agent is running, log lines, token usage. There's also a Human Input Panel that appears when the backend pauses for user input."
